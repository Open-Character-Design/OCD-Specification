# Open Character Design Specification – Legend (v1.0)

The legend is the canonical companion to `spec/core.schema.json`. It
summarises the structural guarantees of the Open Character Design Specification
(OCD) and describes how definition documents should be authored so that
validators, engines, and pipelines observe the same semantics.

## Root entities

OCD separates timeless authorial intent from runtime state by defining
two root documents:

- **CharacterDefinition** – captures the stable description of a
  character. Definitions store provenance metadata and are intended to
  remain consistent across ports and adaptations.
- **CharacterInstance** – records per-save or per-session runtime state
  for a character that already has a corresponding definition. Instances
  are ephemeral and may be regenerated by a simulation or game engine.

| Key | Required | Purpose |
| --- | --- | --- |
| `kind` | ✅ | Must equal `"CharacterDefinition"` so validators can
  dispatch correctly. |
| `ocd_version` | ✅ | Semantic version of the OCD feature set the document
  targets (e.g. `"0.9.0"`). |
| `$schema` | ➖ | Optional draft-2020-12 schema URI for downstream tooling. |
| `$id` | ➖ | Optional URI identifier for schema-aware repositories. |
| `id` | ✅ | Stable UUID for the definition record. |
| `slug` | ✅ | Lowercase, normalised token used in URLs and references. |
| `names` | ✅ | Canonical labelling block (see below). |
| `identity` | ✅ | Taxonomy, sapience, pronouns, ages, and continuity info. |
| `appearance` | ⭐ | Recommended baseline measurements, forms, and
  portraits. |
| `metaphysics` | ➖ | Optional power systems, abilities, constraints, and
  vulnerabilities. |
| `personality` | ➖ | Optional trait bundle, motivations, and speech
  cues. |
| `background` | ⭐ | Recommended biography, affiliations, relationships, and
  milestones. |
| `behavior` | ➖ | Optional behaviour directives, AI hooks, and runtime
  policies. |
| `media_profiles` | ➖ | Optional domain-specific payloads (e.g. `game_rpg`,
  `fighting`, `visual_novel`). |
| `meta` | ✅ | Provenance, authorship, rights, and required versioning
  timestamps. |
| `extras` | ➖ | Vendor-specific extensions that do not fit core fields. |

### Names block

Every definition must supply a `names.canon` string that uniquely
identifies the character in human-readable form. Optional supporting
fields include:

- `names.display`: ordered list of `{ text, lang }` entries for locale-
  specific presentation.
- `names.aliases`: additional labels or nicknames. Validators deduplicate
  and normalise tokens to avoid clashes with the canonical name.

### Identity and composite personas

The `identity` block describes what the character is and how it presents
across continuities. It supports composite identities through the
`composite_of` array. Each member includes:

- `ref`: UUID of a constituent definition.
- `control_share`: real number between 0 and 1 describing the share of
  agency contributed by the constituent. Validators ensure the sum of
  shares does not exceed 1.
- `exposure`: `"public"` or `"secret"`, which is cross-checked against
  `secret_identities` to catch contradictory disclosures.

`secret_identities` allows authoring alternative personas that should be
kept hidden in-world. Each secret entry tracks a `public_name` and an
`exposure_risk` scalar between 0 and 1 so automated tooling can assess
likelihood of discovery.

### Provenance metadata

`meta.versioning` is mandatory. Both `created_at` and `last_modified`
must be ISO 8601 date-time strings so automated pipelines can guarantee
reproducible diffs and audit history. Additional optional subfields
include:

- `meta.creators`: contributions with role labels.
- `meta.rights`: rights-holder statements, licences, and usage notes.
- `meta.external_ids`: mapping to catalogues (e.g. Wikidata, IMDb).
- `meta.tags`: project-specific classification tokens.

## CharacterInstance top-level keys

| Key | Required | Purpose |
| --- | --- | --- |
| `kind` | ✅ | Must equal `"CharacterInstance"`. |
| `ocd_version` | ✅ | Version of the runtime state format. |
| `$schema`, `$id` | ➖ | Optional schema metadata for tooling. |
| `instance_id` | ✅ | UUID representing this specific runtime snapshot. |
| `from_def` | ✅ | UUID reference to the source CharacterDefinition. |
| `state` | ✅ | Live telemetry such as location, resources, active forms,
  and cooldowns. |
| `progression` | ➖ | Optional levelling data, experience totals, and
  unlock states. |
| `session` | ➖ | Optional save-slot, campaign, or session bookkeeping. |
| `extras` | ➖ | Runtime-only extensions for engine-specific payloads. |

Instances intentionally do **not** include the authorial blocks from the
definition. Engines are expected to merge the definition with an
instance at runtime when presenting a playable character record.

## Trait kinds

OCD traits share a `kind` discriminator and are normalised so that
validator behaviour is consistent across toolchains:

- **BipolarTrait** – expresses an axis between two labelled poles.
  Values must be in the range `[-1, 1]`. Pole labels and keys are
  normalised using the slug rules below.
- **ScalarTrait** – continuous value. Defaults to `[0, 1]` unless the
  author supplies an explicit `scale.min`/`scale.max` range.
- **CategoricalTrait** – selects one item from an allowed set. Values are
  normalised tokens and should align with the project’s trait legend.
- **FlagTrait** – boolean marker for binary characteristics.
- **ProfileTrait** – keyed object of facet → scalar pairs. Keys are
  normalised with the same canonicalisation logic as other trait labels
  so duplicates collapse correctly.

All trait keys are deduplicated after normalisation, and composite
legends must document custom keys so they can be reconciled with the core
trait registry.

## Normalisation rules

Validators perform a series of string and token normalisations to keep
records portable:

- **Slug canonicalisation** – map the Unicode arrow (`⇒`) and underscores
  (`_`) to hyphens, collapse repeated separators, trim leading/trailing
  hyphens, and lowercase the token.
- **Trait axis keys** – run through the same slug canonicaliser so
  `introversion⇒extraversion`, `introversion_extraversion`, and
  `introversion-extraversion` resolve to the same axis.
- **Case folding** – array-like fields such as `tags`, `media_targets`,
  `genres`, and `media` are lowercased and deduplicated during
  normalisation.
- **Unicode** – authorable text should be NFC-normalised; validators warn
  when incompatible control characters are found.
- **Physical quantities** – measurements must be authored as `{ value,
  unit }` objects. Naked numbers are rejected so units remain explicit.

Following these rules keeps CharacterDefinition and CharacterInstance
files interoperable across runtimes and ensures both the Python and Node
validators emit consistent diagnostics.
